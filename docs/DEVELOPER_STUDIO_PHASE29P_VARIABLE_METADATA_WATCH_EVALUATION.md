## GXSM ownership and representation

The codebase uses `GXSM` as the magic/tag for the freestanding compiler’s bootstrap source-map trailer. The repository does not document an expansion of the letters, so this report does not invent one.

The producer is the Server bootstrap compiler: `compiler_driver.cpp` calls `append_bootstrap_source_map()` after the final ELF image is built; `elf_writer.cpp` appends the source map and variable table to that same ELF. Compiler object serialization/linking carries the variable records until final image emission. This is not a sidecar file.

The final-image trailer has versions 1 and 2. Version 1 has a 40-byte header and source mappings only. Version 2 has a 48-byte header and adds variable count/byte count at offsets 40/44. The payload is followed by an 8-byte footer (`GXME` and payload length). The header includes source-file/function/mapping counts, code file offset and code size, payload byte count, and an FNV-1a 64-bit checksum; the checksum field is treated as zero while hashing. The v2 variable record is 100 bytes: source-file/function indices (u16 each), kind/type/location/flags (u8 each), width, declaration byte offset/line/column (u32), signed frame offset (i32), live start/end (u32), and fixed 64-byte name. Source-file rows are 268 bytes, function names 64 bytes, and source mappings 24 bytes.

The current compiler bounds are: at most 16 translation units, 16 functions per unit (256 linked function rows), 256 linked source mappings, and 36 debug variables per unit (4 parameters plus 32 locals, 576 linked variable records). The final bootstrap ELF limit is 98,304 bytes. Source paths have 256-byte storage, function/variable names 64-byte storage. The hosted parser checks trailer bounds and exact size accounting, supported version/header size, checksum, counts, NUL-terminated fixed strings, source/function indices, source mapping code ranges, variable record fields, live ranges, and frame-relative locations before use. Malformed source-map headers and records are rejected with bounded error text. No Phase 29P ABI layout was changed.

Current diagnostics report absence through `present=0 valid=0 mappings=0 image_bytes=...`; malformed trailer/header/checksum/counts/records produce bounded failure text, and exact artifact identity mismatch is rejected before expression evaluation. The parser currently groups an unsupported trailer version with `GXSM header or checksum is invalid` and excessive counts with `GXSM counts are invalid`; it does not expose distinct stable Phase 29P marker categories for unsupported version versus malformed input versus capacity exceeded. This instrumentation request remains incomplete. No separate metadata file is opened, so file-open/read states do not apply.

The runtime consumer is `NativeAppDebugger`: on registration it copies the selected `NativeElfImage.imageBytes` and parses any GXSM trailer from those exact bytes. `InspectVariables` resolves records against the current function and PC, then reads a bounded RBP-relative slot from the owned paused stack. `EvaluateExpression` rebuilds the selected frame’s stack/variable snapshot for the current request and invokes `native_debug_watch_evaluate()`. Developer Studio’s separate DWARF mapper supports source lines, functions, stack frames, and locals/arguments, and also understands a complete GXSM source map; the hosted watch callback uses the Server runtime’s GXSM variable records. The separate DWARF watch evaluator is not the evaluator called by this hosted Server callback.

GXSM does not define stable standalone variable IDs, expression bindings, or a general C/C++ type system. A variable’s bounded identity is contextual: exact executable identity plus source file/function index, parameter/local kind, name/declaration, type/location, and live code range. Same-name variables in different functions therefore remain distinct. There is no distinct GXSM generation/hash: the trailer is authenticated by the exact containing executable identity.

Current records describe only initialized, stable AMD64 frame slots: location `RbpRelative`, signed 32-bit integer (4 bytes) or raw pointer (8 bytes), parameter or local, owning function, and final-code live start/end. There are no register, absolute, constant, or indirect locations in this format. Unsigned and boolean scalar records are not supported. The server validates frame ownership and bounds before reading the slot; a rejected frame/location or failed stack read returns a bounded failure. No raw `counter` slot was read in the Phase 15 hosted run because no authoritative GXSM record existed.

## Why Phase 15 has no GXSM

The Phase 15 fixture is built by its own CMake/build script with Clang++ and LLD for `x86_64-unknown-elf`. Its `DebugSymbols` configuration uses `-O0 -g` and retains DWARF; it does not invoke the Server bootstrap compiler or its `append_bootstrap_source_map()` final-image writer. The resulting image has DWARF but no `GXSM` magic/trailer. The exact artifact selected for the fresh no-GXSM session was:

- Project `com.example.debuggerphase15`, project generation 1, build operation 2, AMD64, configuration `DebugSymbols`.
- Artifact/module and symbol generations: no separate artifact generation; loaded module generation 1 and DWARF symbol generation 1. GXSM generation is absent.
- Project-relative executable: `build/bin/amd64/debugger-phase15.elf`.
- Artifact size 12,984 bytes; SHA-256 `8B1511A99BF7E68EF5BF5D464984EAF745D771E916FBAEA751F32EC7314A0AA4`.
- No GXSM marker was present in the exact ELF bytes; there is no metadata sidecar path, GXSM version, trailer size/hash, or `counter` GXSM record to report.

The host validated the completed-build artifact hash and loaded DWARF (symbol generation 1); the selected execution and debug artifact were the same project ELF. Breakpoint remapping and source mapping worked. That evidence rules out metadata staging/selection as the cause. This is neither a Server compiler’s failure to emit records for its supported C subset nor a case of metadata being discarded. The Clang C++ fixture does not implement the Server bootstrap metadata-emission step. This remains optional for launching/debugging: breakpoints and stepping operate through DWARF even with no GXSM.

For the Phase 15 source, `counter` is declared as a local `int` inside `debugLoop` at `src/main.cpp:34`; the loop continues through lines 37–40 and the fixture breakpoint is line 42. The intended source scope is within `debugLoop`; Step Over returns to `debugCaller` at line 48 and Step Out reaches `gx_main` at line 59. No GXSM `counter` record exists, so there is no metadata type/record identity/live code range/frame offset to report. Without that record and stop-specific storage description, Phase 29P cannot claim the precise machine-code live range, raw value, comparison result, or explicit GXSM `OutOfScope` status at any of those PCs.

## Build/artifact identity, frame and stop ownership

The Studio symbol mapper associates its loaded data with project ID, target profile, architecture, normalized executable path, executable size, SHA-256, project generation, build operation, and mapper generation. The Server watch request also carries the expected artifact SHA-256 and session/target handle, process/runtime, thread, stop generation, and selected frame index. Runtime lookup must match the registered image and exact current paused context. A separate symbol/GXSM generation is not stored in the trailer; the containing image hash and runtime registration provide that binding. The hosted run used module generation 1 and symbol generation 1; there was no GXSM generation.

An expression request is reevaluated against the current selected frame (`auxiliaryAddress`) and current stack snapshot; a missing/invalid frame is rejected. The parser/evaluator itself verifies paused state and variable snapshot session/stop generations. Continue invalidates the controller’s old stopped inspection state, and delayed stale generations are rejected by the existing API ownership checks. The hosted Phase 29O fixture used frame 0. The current Phase 29P run did not switch the selected frame, so the frame-switch branch is covered by implementation identity checks but was not independently accepted by a hosted frame-change gate.

The no-GXSM fresh hosted lifecycle passed 1/1: initial breakpoint mapping and debug start succeeded; locals were available through DWARF; the watch `counter == 2` returned API status 6 / error category 13 (metadata unavailable) at stop 1 and was freshly requested again at stop 6, with no accepted/cached value. Step Into, Step Over, and Step Out reached stops 6, 10, and 11; the debugger continued, invalidated inspection while Running, exited, and tore down target/session/window cleanly. The smoke gate also rejected the internal Step Out trap as not being a user pause. The script gate asserts metadata-unavailable at stops 1 and 6; it does not establish successful or out-of-scope watch resolution at stop 10/11. Historical Phase 29O stepping evidence covers its 5/5 and 25/25 stepping sessions, but not a positive GXSM watch value.

The current image is not a separately paired sidecar, so an old metadata file cannot be selected by matching source names. A generic wrong-artifact SHA-256 request is rejected in the native debugger runtime regression. No test injected a stale GXSM trailer, performed a source rebuild A→B, or proved a positive-GXSM relaunch. The Phase 29O fresh-process lifecycle did verify clean no-GXSM relaunch/teardown and no prior runtime value carrying over. No metadata, raw value, watch result, or frame association survives as a current positive watch value in this absent-metadata case.

## Watch expression and repair

The shared Server evaluator already had bounded variable lookup, decimal/hex integer literals, parentheses, unary `+`/`-`, and checked signed 64-bit `+`, `-`, `*`, `/`, `%`, with explicit errors for parse errors, unknown/non-live names, unsupported types/operators, divide-by-zero, overflow, stale generation, running state, and unavailable metadata. Limits include 256 expression bytes, 64 tokens, 64 AST nodes, 16 parser levels, 32 evaluation levels, 64-byte identifiers, and 32-byte literal text. Before this change `==` was rejected as an unsupported operator. The separate DWARF watch parser already recognized comparison tokens, but that is not the parser used by the hosted Server watch route.

The Server evaluator now recognizes signed-integer `==` at lower precedence than arithmetic and yields signed integer `1` or `0`; one `=` and other unsupported operators remain errors. New tests use production evaluator code for true/false `counter == integer`, arithmetic precedence, and parenthesized arithmetic. Therefore the expression semantics are now correct when given a valid current variable snapshot. In the Phase 15 hosted session the expression did not reach that stage: `counter == 2` remained `MetadataUnavailable`, so no boolean or raw `counter` value is claimed. Locals remain DWARF-backed while the hosted watch is GXSM-backed; because no GXSM snapshot exists, locals/watch value consistency could not be compared.
